# 《千禧年购物指南》玩法 Demo 开发计划

状态：Checkpoint 0（规则与数据骨架）和 Checkpoint 1（拼图实验室）已完成首版实现；下一阶段是 Checkpoint 2（购物、无限背包与原子结账）。

## 1. Demo 目标

这个 Demo 首先验证以下问题：

1. 在商店之间寻找合适形状和属性的商品，是否能形成有意义的购买决策。
2. “先试摆、再结账”的流程是否顺手，是否真的能让空间利用率影响花费。
3. Polyomino 精确填充、属性主导条件和经济压力结合后，是否有趣而不容易卡死。
4. 地图、营业表、购物、背包、任务和推进世界阶段能否组成完整循环。

Demo 不承担正式剧情、美术表现、完整对白或最终数值平衡。视觉上统一使用色块、普通几何图形和占位文字；商场主地图使用 `res://pic/map.png`。

### 完成定义

玩家可以不限天数地游玩，访问五家按日程营业的商店，并完成三个事件。完成第三个事件后显示 Demo 完成总结，但允许继续逛店和测试系统。

## 2. 已锁定的玩法规则

### 2.1 时间、收入与世界阶段

- 初始为第 1 天，初始资金 100 元。
- “下一天”按钮始终可用。
- 每进入新的一天：资金增加 100 元、普通商品库存刷新、营业店铺变化。
- 钱可以跨天累计，不设上限。
- 日历天数和世界阶段解耦。玩家可以反复过日子攒钱，不会错过事件。
- 世界阶段只因关键事件完成而推进；它负责解锁下一件特殊商品和下一事件。
- Demo 阶段不设置每天结束的强制条件。

### 2.2 商店

五家商店为：

| 商店 | 主要属性 | Demo 中的作用 |
| --- | --- | --- |
| 书店 | 雾（紫） | 提供规整、容易使用的填充件 |
| 快餐店 | 花（粉） | 提供花属性填充件和第二件特殊商品 |
| 唱片店 | 灯（黄）、镜（蓝） | 提供两类属性填充件和第三件特殊商品 |
| 花店 | 灯（黄）、雾（紫） | 提供属性调整件和异形骨牌 |
| 玩具店 | 镜（蓝） | 提供镜属性填充件和第一件特殊商品 |

- 每天开放三家店。
- 商场地图始终展示完整一周排班和各店当日状态。
- 关闭的商店仍可点击，但只显示“今日休息”和营业告示，不能购物。
- 普通商品每天按 SKU 刷新限额；未售库存不会累积到下一天。
- 特殊商品只能购买一次，购买后永久下架。

暂定七日循环排班：

| 星期 | 营业店铺 |
| --- | --- |
| 一 | 书店、玩具店、快餐店 |
| 二 | 唱片店、花店、书店 |
| 三 | 玩具店、快餐店、唱片店 |
| 四 | 花店、书店、玩具店 |
| 五 | 快餐店、唱片店、花店 |
| 六 | 书店、玩具店、快餐店 |
| 日 | 唱片店、花店、书店 |

该排班保证任一家店最多只连续休息一天。第 8 天重新使用星期一排班，但日历天数继续增长。

### 2.3 物品与背包

- 每个物品实例有唯一 ID，同一时刻只能位于无限背包、一个未完成任务格阵或购物车试摆区之一。
- 每种物品固定绑定名称、商店、形状、属性、价格和每日库存。
- 每件物品只有一种属性，属性值等于其占据的格子数。
- 属性映射：黄＝灯、蓝＝镜、粉＝花、紫＝雾。
- 物品只能进行 90 度旋转，不能镜像翻转。
- 右键顺时针旋转；如果旋转后越界或重叠，则保留原姿态并给出明确反馈。
- 每家店都有昂贵的 1×1 商品作为解卡手段，但每天库存有限。
- 未提交的物品可以在格阵和背包之间任意移动。
- 提交任务后，任务中的特殊物品和普通物品全部消耗，事件永久完成。

### 2.4 拼图任务

- 格阵是一个带遮罩的不规则二维网格。
- 合法提交必须满足：所有可用格恰好填满、无重叠、无越界、包含指定特殊物品，并满足事件属性条件。
- 可以同时持有和推进多个事件任务。
- 任务栏左侧为无限背包，右侧为当前任务格阵；可以通过标签切换任务。
- 每个格阵实时显示灯、镜、花、雾四项总值，并清晰标出当前最高属性和任务要求。
- 任务只能在对应老板处通过“交谈／提交任务”完成，不能直接在任务栏远程提交。

三个事件的属性判定暂定为：

1. 事件一：镜必须严格高于灯、花、雾。
2. 事件二：灯或花必须成为主导属性；灯与花可以并列，但它们的值必须严格高于镜和雾。
3. 事件三：无属性限制，只检查形状和特殊物品。

### 2.5 购物、试摆与结账

购物界面采用同屏布局：

- 左侧：当前商店商品，可切换到无限背包。
- 右侧：任务列表和当前任务格阵。
- 下方：购物车、总价、当前资金、结账按钮和退出按钮。

交易规则：

1. 当前商店尚未购买的普通商品可以加入购物车，并直接拖入已解锁任务中试摆。
2. 背包已有物品也可以同时参与试摆；它一旦放入格阵，就真实地从背包移动到该格阵。
3. 购物车商品只是临时实例，结账前不属于玩家；UI 必须用边框或角标与已拥有物品区分。
4. 结账是原子操作：重新检查资金、库存和摆放合法性，成功后统一扣款并把购物车实例转为已拥有实例。
5. 购物车商品既可以放在任务中，也可以选择结账后直接进入无限背包。
6. 结账前可以任意撤销购物车商品。退出商店时，所有未结账商品及其试摆位置被清除。
7. 退出商店、取消购物车或结账失败，不得改变已拥有物品的位置。
8. 已结账商品不能退款；未提交任务中的已拥有物品仍可取回背包。
9. 特殊商品结账成功后才创建对应任务。它不参与购买前对尚未解锁任务的试摆；解锁后自动进入无限背包，并打开一次新任务提示。

### 2.6 中英文切换

- 项目从 Demo 阶段开始同时支持简体中文（`zh_CN`）和英文（`en`），不把本地化推迟到内容完成后。
- 使用 Godot `TranslationServer` 和 PO 翻译资源；商品、任务、商店、按钮、状态和错误原因全部保存翻译键，不在 UI 或规则脚本中硬编码显示文本。
- 所有主要界面提供常驻语言切换按钮，切换立即生效，不要求重启场景或游戏。
- 玩家选择写入 `user://settings.cfg`，下次启动沿用；首次启动按系统语言选择中文或英文，无法识别时回退英文。
- 每次界面验收都同时检查中文和英文，尤其关注英文长度导致的按钮、商品卡和任务说明溢出。

## 3. Demo 内容基线

这些数值用于首轮实现和测试，不视为最终平衡。Checkpoint 6 会根据实际试玩调整。

### 3.1 价格曲线

目标是让大骨牌每格更便宜，1×1 最灵活但最昂贵：

| 大小 | 普通商品参考价格 | 每格参考价格 |
| ---: | ---: | ---: |
| 1 格 | 10 | 10.0 |
| 2 格 | 12 | 6.0 |
| 3 格 | 14 | 4.67 |
| 4 格 | 16 | 4.0 |
| 5 格 | 18 | 3.6 |

- 普通 1×1 商品每日库存为每店 3 个。
- 2–3 格普通商品每日库存为 2 个；4–5 格商品每日库存为 1 个。
- 每家店每天共有 4 个普通 SKU、7 件商品；每天开放三店，共刷新 21 件普通商品。
- 特殊商品价格为 20–22 元，终身限购 1 件，不参与每日刷新。
- 三个已验证基准解分别花费 82、96、120 元。前两件可以用一份工资解决，第三件可以使用前两次的结余；买错或大量使用 1×1 时，可以多过几天补充资金。

### 3.5 三个事件格阵

格阵中的 `#` 是必须填充的有效格，`.` 是不可占据的透明格。规划阶段已经用“允许旋转、禁止镜像”的精确覆盖枚举验证了下面三套基准解。

- 有效格：19。

- 必需物品：缺耳泰迪熊 P5。
- 属性条件：镜严格高于灯、花、雾。
- 难度定位：教学。轮廓小、凹槽少，但已经要求使用旋转和观察属性。

.#.#.

### 3.6 格阵显示尺寸

- 逻辑格阵均使用整数格坐标，不与图片像素绑定。
- 以 1280×720 的首版窗口计算，任务格单边暂定 56 px。
- 最大的金鱼格阵显示宽度为 504 px，能够和左侧商品／背包栏同屏。
- 鼠标命中区使用完整格子，不要求点击物品的不规则可见区域。
- 后续可以在 44–64 px 之间统一缩放，但不改变格阵逻辑尺寸。

每个任务必须放入对应特殊商品。Checkpoint 1 还会把规划阶段的枚举检查沉淀为项目测试，要求：

- 至少存在一个不用 1×1 的经济解。
- 至少存在一个允许使用 1×1 解卡的宽松解。
- 不存在仅凭特殊物品就完成或完全没有旋转需求的退化解。
- 属性任务至少存在两个来自不同商店组合的合法购买路线。
- 泰迪熊和金鱼的推荐解不超过一份工资；磁带推荐解不超过一份工资加前两题推荐解的累计结余。

### 3.7 世界阶段与购物清单

- 阶段 0：购物清单指向玩具店的“缺耳泰迪熊”。
- 完成事件一后进入阶段 1，清单指向快餐店的“吃剩的鱼骨”。
- 完成事件二后进入阶段 2，清单指向唱片店的“反复倒带的磁带”。
- 完成事件三后进入阶段 3，弹出 Demo 完成总结。
- 如果目标商店当天休息，清单直接显示其下一次营业日，不让玩家猜测。
- 特殊商品买完但任务未完成时，购物清单改为“完成对应事件”，商品不再出售。

## 4. 界面与交互结构

### 4.1 商场地图

`pic/map.png` 作为全屏底图，上方叠加五个透明热点和简洁店名牌。首版不要求热点严格匹配图片中的真实门面，只要求空间分布稳定、容易点击。

常驻 HUD：

- 当前天数、星期和资金。
- 当前购物清单目标。
- “任务栏”按钮和未完成任务数量。
- “营业表”按钮。
- 始终可用的“下一天”按钮。
- 常驻的“中文／EN”语言切换按钮。

### 4.2 商店界面

- 使用统一商店场景，根据数据替换店名、老板占位形状、属性色和商品列表。
- 一级操作只有“交谈／提交”“购物”“离开”。
- 对话仅使用短占位文本，用于证明事件状态能够改变交谈选项。
- 关闭商店使用轻量提示层，不进入完整商店 UI。

### 4.3 任务和购物同屏

- 任务栏与购物界面共享同一个背包组件和拼图格阵组件，避免出现两套操作规则。
- 商品卡片显示：名称、形状预览、属性、格数、价格、库存、是否已拥有／未结账。
- 拖动时显示网格吸附预览：合法为亮色，重叠或越界为红色。
- 格阵旁显示覆盖进度、四属性数值、属性要求是否满足、特殊物品是否已放入。
- 提供“全部取回背包”和“撤销上一步”，但不提供自动解题。

### 4.4 下一天

点击后显示简短结算层：

- 天数和星期变化。
- “上班收入 +100”。
- 今日营业的三家店。
- 商店库存已刷新。

如果当前存在未结账购物车，必须先给出确认并取消购物车；已拥有物品在未完成格阵中的摆放在当前运行期间保留。

## 5. 技术结构规划

### 5.1 数据驱动资源

计划建立以下定义资源，避免把 Demo 数值写死在 UI 脚本中：

- `ItemDefinition`：ID、名称、商店、局部格坐标、属性、价格、库存、是否特殊。
- `TaskDefinition`：ID、遮罩格、必需特殊物品、属性规则、提交商店、解锁阶段。
- `ShopDefinition`：ID、名称、属性色、商品表、周排班。
- `WorldStageDefinition`：阶段、购物清单、可用特殊商品、完成条件。

运行时数据使用唯一实例 ID 区分同种商品的多个副本。

### 5.2 运行时状态

单一 `GameState` 负责：

- 天数、资金和世界阶段。
- 每日商店库存。
- 已购买特殊商品、背包物品和已完成任务。
- 当前未完成任务及运行期间的摆放位置。
- 发出状态变化信号，UI 只显示状态，不自行修改经济数据。

交易由独立 `ShopTransaction` 执行，确保扣钱、扣库存、创建物品和保留试摆位置要么全部成功，要么全部不发生。

拼图合法性由不依赖 UI 的 `PuzzleRules` 计算，输入任务、物品及其坐标和旋转，输出：

- 越界格、重叠格和未覆盖格。
- 特殊物品是否存在。
- 四种属性总值和当前主导属性。
- 是否可以提交以及失败原因列表。

### 5.3 场景边界

计划场景组件：

- `Main`：页面状态和全局 HUD。
- `MallMap`：底图、店铺热点和营业状态。
- `ShopScreen`：老板占位、交谈与购物入口。
- `ShoppingPanel`：商品、背包、购物车和结账。
- `TaskPanel`：任务标签、背包和格阵。
- `PuzzleBoard`：网格、拖放、吸附、旋转和合法性反馈。
- `DayTransition`：下一天结算。
- `DemoComplete`：完成总结。

购物界面和普通任务栏复用同一个 `InventoryPanel`、`PuzzleBoard` 与拖放控制器。

### 5.4 存档范围（方案 B）

自动存档以下内容：

- 天数、资金、世界阶段。
- 已完成事件和已购买特殊商品。
- 当前背包中以及未完成任务中所有已拥有物品实例。
- 当日普通商品剩余库存。

不保存：

- 未结账购物车。
- 未完成格阵的具体位置和旋转。

加载时，所有属于玩家但原本位于未完成格阵的物品统一回到无限背包。这样既不会丢物品，也不需要在 Demo 阶段维护布局版本兼容。

存档时机：成功结账、完成任务、进入下一天以及退出到桌面前。

## 6. 开发顺序与 Checkpoint

每个 Checkpoint 都必须先通过 `tools/check.ps1`；需要编辑器交互时还要通过 `tools/check-mcp.ps1`，运行项目检查日志和截图后才交给用户试玩。

### Checkpoint 0：数据骨架与可测试规则层

实现范围：

- 建立目录、主场景壳、输入动作和数据资源基类。
- 实现 Polyomino 坐标归一化、90 度旋转和形状预览数据。
- 实现任务遮罩、属性规则及商品／任务数据校验。
- 建立精确覆盖测试辅助器，用来验证三个任务至少有合法解。

自动验收：

- 旋转四次回到原形；不同初始偏移归一化后相同。
- 数据 ID 唯一，价格、库存和形状均合法。
- 三个任务定义可加载，特殊物品尺寸不超过格阵。

本阶段没有完整可玩内容，不要求用户试玩。

### Checkpoint 1：独立拼图实验室

实现范围：

- 一个不经过地图和商店的拼图测试场景。
- 背包拖入、拖回、网格吸附、右键旋转、重叠／越界反馈。
- 精确填满、特殊物品检查、属性实时统计和三种任务条件。
- 撤销一步、全部取回、切换三个测试任务。

自动验收：

- 放置、移动、旋转、取回不会复制或丢失物品。
- 精确填满与属性规则覆盖边界情况和并列情况。
- 每个任务至少有一组经过测试固定下来的基准解。

用户试玩重点：

- 拖动吸附是否准确。
- 右键旋转是否符合直觉。
- 错误反馈、属性统计和“为什么不能提交”是否看得懂。
- 三个格阵从教学到进阶的难度是否合理。

这是第一个核心玩法验证点；如果拼图本身不顺手，先在这里调整，不继续堆商店系统。

### Checkpoint 2：购物、无限背包与原子结账

实现范围：

- 单个测试商店、资金、库存、购物车和无限背包。
- 商店商品与已有物品共同试摆。
- 未结账角标、总价、资金不足、库存变化、取消和退出回滚。
- 成功结账后，试摆商品原地转为已拥有物品。

自动验收：

- 资金或库存不足时不产生部分扣款。
- 退出商店只清除购物车商品，不移动已有物品。
- 同一实例不能同时出现在背包和格阵。
- 结账后金钱、库存、背包和格阵归属保持一致。

用户试玩重点：

- “商品／无限背包”切换是否顺手。
- 已拥有与未结账商品能否一眼区分。
- 试摆、撤销、退出和结账是否符合预期。
- 同屏信息是否过密。

### Checkpoint 3：第一事件纵向切片

实现范围：

- 使用 `pic/map.png` 的商场地图和玩具店热点。
- 初始 100 元、购物清单、玩具店商店界面。
- 购买“缺耳泰迪熊”后解锁事件一。
- 购买普通件、完成镜属性要求、回玩具店交谈提交。
- 消耗物品、完成事件并推进世界阶段。

自动验收：

- 特殊商品只能买一次，任务只触发一次。
- 无特殊物品或镜不是严格最高时不能提交。
- 合法提交会准确消耗格阵物品，并永久标记事件完成。

用户试玩重点：

- 从地图到商店、任务、再回老板提交的完整循环是否清楚。
- 购物清单能否自然引导而不需要教程长文。
- 一次事件的操作长度和购买决策是否有趣。

这是第一个真正端到端可玩的版本。

### Checkpoint 4：五店、日历和多任务系统

实现范围：

- 五个地图热点、统一商店界面和全套普通商品。
- 七日循环排班、关闭告示、营业表。
- 下一天始终可用，工资增加、库存刷新、钱跨天保留。
- 多任务标签和跨商店购买。

自动验收：

- 连续推进至少 21 天，星期、资金和库存均正确。
- 每天恰好三店营业，任一家店最多连续休息一天。
- 下一天不会复制或遗失背包、格阵中的已拥有物品。
- 关闭商店不能购物，开放后库存正确刷新。

用户试玩重点：

- 地图热点、今日营业和下一营业日是否清晰。
- 多次过日子的节奏是否拖沓。
- 在不同店之间寻找属性和形状的过程是否产生计划感。

### Checkpoint 5：三事件与完整世界阶段

实现范围：

- 接入金鱼事件和磁带事件。
- 三种属性条件、三套特殊商品、提交老板及占位事件文本。
- 阶段购物清单、事件完成反馈和 Demo 完成总结。
- 完成后继续游玩的入口。

自动验收：

- 三事件能按阶段依次解锁且不能重复完成。
- 玩家无论经过多少日历天都不会错过事件。
- 每个事件的基准解、宽松解和属性路线都能通过。
- 三事件全部完成后只触发一次完成总结。

用户试玩重点：

- 三次循环是否有足够变化。
- 属性限制是在增加决策，还是只增加计算负担。
- 第二、第三事件的难度增长是否自然。
- 完成总结出现时，是否觉得已经体验了一个完整系统。

### Checkpoint 6：经济平衡与解卡审计

实现范围：

- 根据前三个可玩版本调整价格、库存、格阵和形状池。
- 统计基准解成本、1×1 宽松解成本和需要访问的商店数。
- 加入资金不足、目标店休息、买错商品等状态下的清晰提示。
- 必要时调整商品形状，不增加额外经济系统。

验收目标：

- 精打细算的玩家能用一份工资解决前两件事件，并用前期结余加第三份工资解决磁带事件。
- 随意购买的玩家最多多工作若干天，不会永久软锁。
- 所有任务都可以仅靠正常刷新库存完成。
- 1×1 可以解卡，但明显比规划良好的组合更贵。
- 不存在某一种普通商品在所有任务中都成为无脑最优选择。

用户试玩重点：购买时是否真的会比较形状、属性和价格，而不是总买同一套商品。

### Checkpoint 7：存档、稳定性与 Demo 交付

实现范围：

- 实现方案 B 存档及“清除存档／重新开始”。
- 完成键鼠操作提示、最小音效占位和统一视觉状态。
- 覆盖窗口缩放、重复进出商店、快速切换任务和连续结账。
- 清理调试入口，但保留开发者测试场景。

自动验收：

- 在购物后、跨天后、事件完成后分别存取档，资金和实例总数不变。
- 未完成布局加载后全部安全返回背包。
- 从全新存档到完成三个事件可连续跑通。
- Godot 导入、GUT、运行日志和 Git diff 全部干净。

用户最终验收：

- 视觉层级是否足以支撑玩法测试。
- 拖放、旋转、购物和提交的手感。
- 哪个事件最好玩、哪里最卡、是否愿意继续逛一天。

## 7. 测试策略

### 必须自动化的确定性逻辑

- Polyomino 旋转、归一化和格占用。
- 越界、重叠、精确填充和特殊物品条件。
- 属性累计、严格最高及灯／花并列规则。
- 库存刷新、收入、星期循环和世界阶段。
- 购物车的成功提交和失败回滚。
- 物品实例所有权守恒：不能复制、丢失或同时出现两处。
- 任务提交后的消耗和防重复提交。
- 存档往返和未完成布局回收。
- 三个任务的固定基准解。

### 必须运行检查的交互内容

- 地图热点是否与底图和窗口缩放一致。
- 拖动、吸附、右键旋转和任务标签切换。
- 购物 UI 和任务 UI 同屏时的遮挡与输入冲突。
- 退出商店、切换任务、下一天时的确认和回滚。
- 运行日志中无脚本错误、孤儿节点或无效资源警告。

### 每个 Checkpoint 的固定交付动作

1. 运行 `pwsh -NoProfile -File tools/check.ps1`。
2. 打开编辑器时运行 `pwsh -NoProfile -File tools/check-mcp.ps1`。
3. 运行相关场景并检查编辑器日志、游戏日志和截图。
4. 分别切换到中文和英文检查文本、布局及交互反馈。
5. 检查 `.tscn`、`.tres` 和 `project.godot` 的 Git diff。
6. 提供一条最短试玩路径和本阶段需要用户判断的手感问题。

## 8. 明确延后到 Demo 之后的内容

- 正式美术、店主立绘、店铺背景和复杂动画。
- 酒精灯小姐、关闭店铺剧情和大量对话内容。
- 基于语义理解的对话或任务推进。
- 每晚必须完成的购物目标或时间压力。
- 物品邻接产生的大量叙事文案和复杂联动。
- 镜像翻转、自动解题、随机生成谜题。
- 退款、出售、折扣、好感度和更多赚钱方式。
- 未完成格阵布局的完整存档。
- 手柄、触摸屏和正式无障碍适配。

## 9. 主要风险与控制方式

| 风险 | 处理方式 |
| --- | --- |
| 拼图操作本身不顺手 | Checkpoint 1 单独验证，不等完整商店建好再测试 |
| 购物临时物品与已有物品混淆 | 明确实例状态、视觉角标和原子交易；用所有权守恒测试覆盖 |
| 属性要求导致有形状解却没有属性解 | 每个任务同时保存经过自动测试的形状与属性基准解 |
| 买错物品后软锁 | 无限天数工资、每日库存刷新、每店有限 1×1 解卡件 |
| UI 同屏信息过多 | 共享组件、商品／背包标签切换、一次只显示一个任务格阵 |
| 五店三事件扩展时出现大量重复代码 | 商店、商品、任务和阶段全部数据驱动，共用统一场景 |
| 后续更换正式素材影响玩法代码 | 地图热点、商品定义和视觉组件分离，不按图片像素硬编码逻辑 |

## 10. 建议的实施边界

开发按 Checkpoint 顺序推进，每个 Checkpoint 都保持主项目可运行。Checkpoint 1、2、3、5、6 是关键试玩节点；收到手感反馈后允许回调格子尺寸、拖放逻辑、价格和格阵，再进入下一阶段。

除非新的试玩结论推翻核心循环，否则不在 Demo 阶段增加新商店、新属性、新货币或复杂剧情系统。
